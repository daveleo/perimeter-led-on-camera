    The LED emits a short pulse of light every 312.5 µs. A person blends those pulses into steady light. A camera at 1/1000 s records a 1 ms slice — about three pulses — and which slice it takes decides what it sees.

    01

    Executive summary

    An LED perimeter display is driven by pulse-width modulation: each LED is switched on and off very rapidly, and brightness is set by how much of each cycle the LED is on. To the eye this is steady light, because human vision blends rapid flicker together. A camera does not. It opens its shutter for a short, precisely timed window and records only the light that arrives during that window.

    Because of this difference, a display that looks perfectly uniform to a person in the stadium can, in a photograph or a broadcast picture, show bands that scroll or sit still, brightness differences between areas, colour shifts, partially lit regions, or flicker between frames.

    These effects are not usually caused by a faulty LED module. They are caused by the timing relationship between several independent clocks: the frame rate of the content (fps), the output refresh of the graphics card (Hz), the input and output frame rate of the LED controller, the frame timing of the receiving cards set by the scan file, the row-scanning frequency from multiplexed scanning, the PWM / grayscale refresh of the driver IC (for example 3200 Hz), the camera frame rate, and the camera shutter time.

    The one relationship to remember A 50 Hz video signal and a 3200 Hz PWM refresh are different layers of the same system. 50 Hz is how often a new picture is delivered. 3200 Hz is how often each LED repeats its pulse pattern inside that picture. They are related — in our example implementation, 3200 ÷ 50 = 64 repetitions per video frame — but they are not the same measurement, and one cannot be substituted for the other.

    What we deliver

    When we design, configure, test and hand over a perimeter system as a 50 Hz system, we expect the customer’s complete signal chain to stay at 50 Hz: media at 25 or 50 fps, graphics card at 50 Hz, controller in and out at 50 Hz, receiving cards and scan file validated at 50 Hz, and the resulting driver-IC PWM/grayscale refresh at the specified value (3200 Hz in our example). The camera settings used on site must be chosen and tested against that configuration. If any link changes — content frame rate, graphics-card output, controller timing, scan file, brightness operating point, or camera exposure — the on-camera behaviour can change and must be re-validated.

    What a spec sheet cannot promise

    A high advertised refresh rate (3200 Hz, 3840 Hz, or higher) reduces the likelihood of visible camera artefacts but does not guarantee a clean picture at every brightness, every content level and every shutter speed. This document explains why, and how to verify performance for a specific installation.

    Scope & assumptions This document is vendor-neutral by design. No proprietary driver-IC, receiving-card or controller datasheets were consulted; every hardware-specific timing behaviour is labelled implementation-dependent or engineering assumption. “50 Hz production environment” means the European broadcast convention (25/50 fps, 50 Hz). All arithmetic uses an explicitly labelled simplified linear PWM model; real driver ICs use S-PWM, distributed / segmented PWM, OE blanking, current gain and sometimes hybrid PWM/PAM.

    The complete timing chain

    The signal path from media file to camera passes through nine stages. A timing error introduced early does not stay local — it is carried forward. Expand any stage below.

    Signal chain — media file to cameratap a stage

    Each stage has its own clock or its own configuration. On-camera artefacts come from how those clocks line up — and a display that is entirely within specification can still show artefacts, because the camera is a second, unsynchronised sampling system.

    Four clocks, four different rates

    Before going further, keep these four apart. They are drawn to scale below for our example configuration.

    The four clocks, to scale (50 Hz · 3200 Hz · 1/8 scan · 1/1000 s)

    One video frame is 20 ms. Inside it, the PWM/grayscale pattern repeats 64 times (312.5 µs each). Inside each of those, a 1/8-scan panel returns to the same LEDs eight times. A 1/1000 s camera shutter (amber) spans just 3.2 PWM periods.

    How a mismatch propagates

    • Content vs GPU (e.g. 30 fps content on a 50 Hz output) → uneven frame repetition → periodic cadence a short shutter freezes as a beat.
    • GPU vs controller (60 Hz in, 50 Hz out with conversion) → dropped / interpolated frames → a slow rolling brightness change on camera.
    • Controller vs scan file (a 60 Hz scan file on a 50 Hz input) → the per-frame PWM budget is wrong → altered grayscale linearity, low-gray banding, a refresh that is not the intended value.
    • Scan file vs camera (a correct 50 Hz / 3200 Hz display, but the shutter captures a partial, phase-dependent set of pulses) → bands and frame-to-frame flicker even though the display is correct.

    What the scan file is and is not

    The scan file is configured for a 50 Hz system. In the specified implementation, its timing parameters produce a 3200 Hz PWM/grayscale refresh at the driver IC. “50 Hz scan file” and “3200 Hz refresh” are not the same number — one is the frame context the file was built for; the other is a timing result the file produces at the LED.

    05

    Relationship between 50 Hz, 3200 Hz and 3840 Hz

    Why the numbers are paired

    In one common architecture, the receiving card and driver IC divide each video frame into a fixed number of PWM/grayscale repetitions to raise the visible flicker frequency. If that number is 64:

    64 × 50 Hz = 3200 Hz   // 3200 / 50 = 64 64 × 60 Hz = 3840 Hz   // 3840 / 60 = 64

    In this architecture, 64 PWM/grayscale repetitions occur during one video-frame period. A system built around 50 Hz frames lands on 3200 Hz; a system built around 60 Hz frames lands on 3840 Hz. That is why the two numbers appear together in product literature.

    This relationship is not universal The 64× ratio is a design choice of a particular receiving-card / driver-IC combination, not a law. Some driver ICs generate PWM timing from an internal oscillator or a GCLK divider that is not phase-locked to the frame rate; their grayscale refresh can be a fixed frequency regardless of whether the frame is 50 or 60 Hz. Some use a different subdivision, a non-integer ratio, or a variable one that depends on bit depth and “performance mode”. Do not assume every 3840 Hz system is 60 Hz, or every 3200 Hz system is 50 Hz. Confirm from the scan file, the driver-IC datasheet, the controller documentation, or physical measurement.

    Multiple frequencies coexist in the light

    The optical output of a scanned PWM display is not a single sine wave. At the same time it can contain a component at the frame rate (50 Hz), a component at the row-scan frequency, a component at the PWM/grayscale refresh (3200 Hz), and harmonics of all three. A camera artefact can beat with any of these — which is why “we have a 3200 Hz display” does not, by itself, answer “will it look clean on camera”.

    06

    How PWM creates brightness

    An LED is essentially a switch for light: at a fixed drive current it is either emitting or dark. PWM sets average brightness by controlling the fraction of each period the LED is on — the duty cycle.

    The period does not change with brightness. Reducing brightness normally shortens the ON pulse and lengthens the OFF gap within the same period. A 3200 Hz PWM display driven dark is still a 3200 Hz PWM display; it just has shorter pulses.

    Simplified model The waveforms and arithmetic below assume: one rectangular ON pulse per period; ON time exactly proportional to the brightness percentage; no gamma, no calibration coefficients, no current-gain change, no OE blanking, no pulse splitting. Real driver ICs deviate from all of these. Use the numbers to understand the mechanism, not to predict a specific waveform.
    ON / OFF time as brightness falls — 3200 Hz, T = 312.5 µs

    At 100% the LED fills the period and the light looks continuous. At 10% it is a ~31 µs spike in ~281 µs of darkness. The refresh is unchanged; the modulation is far deeper — and that is what a fast shutter resolves.

    Global brightness versus content brightness

    Six things all make an LED “dimmer”. They are not implemented the same way and do not behave the same on camera.

    Six ways to be darker
    MechanismWhat physically changesTypical layer
    1 · Global display brightness = 10%Every pixel scaled down togetherController / receiving card; may be PWM duty, current gain, or a mix
    2 · Pixel with 10% grayscale valueOnly that pixel’s code value is lowContent → gamma + calibration + driver mapping
    3 · Dark colour, unequal RGBEach channel at a different low duty/levelPer-channel in the driver IC
    4 · Reduced LED current gainCurrent amplitude lower; pulse width may be unchangedDriver-IC current setting
    5 · Reduced brightness via PWM / OE dutyON time shorter; amplitude unchangedDriver-IC PWM + receiving-card OE
    6 · Current gain + PWM scaling combinedBoth amplitude and width reduced, by a vendor-chosen splitController + receiving card + driver IC

    Mechanisms that work by shortening pulses (2, 3, 5, and the PWM part of 6) make the light more strongly modulated in time — deeper dark gaps between shorter spikes — so a short shutter is more likely to catch a non-representative slice. Mechanisms that work by lowering amplitude (4, and the current-gain part of 6) keep the pulse wide but dimmer, which is generally kinder to cameras — at a cost (section 08).

    Conceptual example only Display brightness 25% × content pixel value 40% → simplified effective level 0.25 × 0.40 = 0.10 → ≈ 10% in the code domain. With display gamma ≈ 2.2 the linear light is nearer 0.25 × 0.402.2 ≈ 0.033 — about 3.3%, not 10%. Calibration coefficients, low-gray algorithms and current-gain interaction move it further. You cannot predict the exact pulse from the percentages; you can predict the direction (dimmer → shorter and/or lower pulses → more camera-sensitive) and must measure the magnitude.
    08

    PWM duty versus LED current gain

    Both reduce brightness. They are different tools with different trade-offs. PWM control changes how long the LED is energised; current-gain control changes the current amplitude while it is energised.

    Same average luminance, two different pulse shapes

    Left: dimmed to 25% by PWM — a short, full-height spike, deep dark gap. Right: dimmed to 25% by current gain — a full-width pulse at reduced height. A slow luminance meter reads them as equal. A fast camera shutter does not.

    • PWM reduction alone, taken far, produces short pulses that make camera artefacts more visible and can crush low grays.
    • Current-gain reduction alone, taken far, keeps pulses long but degrades colour accuracy, calibration validity, low-gray linearity and signal-to-noise.
    • Most professional systems use a combination — a moderate current-gain reduction plus PWM scaling for fine control, with the split chosen by the vendor’s processing. Current-gain reduction is not universally superior.
    Why two “identical” displays differ on camera Two displays with the same measured average luminance and the same advertised refresh can still look different on camera, because pulse shape, pulse distribution across the frame, current amplitude vs duty split, scan timing, OE intervals and low-grayscale processing are not captured by those two figures.

    Effect of scan ratio

    To save driver channels and wiring, many panels share each set of driver outputs between several row groups and light them in sequence. While one group is driven, the others are dark. So a given LED’s maximum possible physical ON time over wall-clock is bounded by its group’s active fraction — even at “100% brightness”.

    Simplified bound The table gives an upper bound on wall-clock ON fraction from scanning alone. It assumes the row-active window is fully usable and ignores OE overhead, blanking, settling and pulse scheduling — all of which reduce it further. Do not simply multiply “scan fraction × grayscale %” and treat it as the real waveform: many driver architectures split and schedule pulses in ways this does not capture.

    • Only selected rows / groups are actively driven during each scan interval; the rest are off.
    • The driver must distribute the grayscale PWM pulses within the available row time, which shrinks as the scan ratio rises.
    • Higher scan ratios can reduce the available physical illumination time per LED, increasing temporal modulation depth and camera sensitivity.
    • Good driver ICs use sophisticated pulse scheduling — splitting each pixel’s energy into several short bursts across the frame — specifically to improve camera performance. This is why the simple bound is only a bound.
    • Perimeter products are frequently designed with low scan ratios to maximise row-active time for cameras; the exact ratio must be read from the scan file, not assumed.
    • Refresh-rate specifications alone do not fully describe the temporal behaviour.
    10

    Why low brightness is harder for cameras

    Take a perimeter display at 10% global brightness, nominal PWM refresh still 3200 Hz, photographed at 1/1000 s. The period remains ≈ 312.5 µs — lowering brightness did not lower the refresh. The ON pulse becomes shorter; the OFF portion becomes longer. A 1/1000 s exposure spans only 3.2 nominal PWM periods. Depending on exposure phase, row-scanning position and pulse distribution, different sensor rows and image areas integrate different amounts of light.

    • At 100% white, the ON pulse fills the available scan window, so during each window the light is comparatively continuous; the exposure captures a fairly representative amount regardless of phase.
    • At 10% brightness or on dark content, the light is a short spike in a long dark period, so which 1 ms slice the camera takes matters a great deal → visible bands, brightness differences, frame-to-frame flicker.
    “Not fully on” is informal — here is the accurate version During its exposure window the camera integrates an incomplete and uneven set of PWM pulses and scan intervals. The number and fraction captured depends on the exposure length, the exposure start phase relative to the PWM and scan clocks, the sensor readout timing, and how the driver distributes pulses. As brightness and content level fall, the pulses get shorter and the dark gaps longer, so the variation between one exposure — or one sensor row — and the next grows. A high advertised refresh rate does not guarantee identical camera performance at every brightness and grayscale value.

    Camera shutter examples

    At 3200 Hz a 1/1000 s exposure captures 3200 × 0.001 = 3.2 PWM periods; at 3840 Hz, 3.84 periods. Neither is a whole number. A non-integer count means the exposure captures “three full pulses plus a bit of a fourth”, and how big “a bit” is depends on where in the cycle the shutter opened. Because camera and display are not phase-locked, that phase is effectively random and drifts frame to frame — so consecutive frames, or consecutive sensor rows, integrate different totals.

    Shutter speed vs PWM periods captured 3200 Hz
    whole number of periods — better average integration fractional — phase-dependent capture

    Hover a bar for the exact count. At 3200 Hz the clean values are 1/50, 1/100, 1/200, 1/400, 1/800 and 1/1600 s.

    An integer period count does not guarantee a clean image Capturing a whole number of nominal PWM periods improves average-light integration but does not defeat: no phase lock between camera and LED; rolling-shutter line-by-line readout; multiplexed scanning (a different clock); OE / blanking timing; distributed / segmented PWM; the actual refresh differing slightly from nominal; low-grayscale algorithms; controller frame boundaries; a drifting exposure start phase; mains-powered venue lighting; other asynchronous displays. Do not claim that 1/800 s will always be clean merely because it covers four nominal PWM periods.

    Camera frame rate as well as shutter

    For a 50 Hz display, a camera at 25 or 50 fps captures a whole number of display frames per cycle and is least likely to beat with the frame layer. A camera at 30 or 60 fps (or 23.976 / 29.97 / 59.94) walks relative to the 50 Hz frame layer, producing a slow rolling brightness/colour change. The beat frequency is |f_cam − n·50| for the nearest integer n — 60 fps gives a ~10 Hz roll.

    Camera-side mitigations

    • Use the camera’s variable / synchro-scan / high-frequency anti-flicker shutter to tune to a value that is clean on this display.
    • Use a flicker-reduction detection mode where available.
    • Choose shutter angles (cine) that correspond to integer PWM captures for the measured refresh.
    • Prefer global-shutter sensors for critical perimeter capture.
    • Genlock the camera to the production reference — this removes the frame-layer beat but not the PWM/scan-layer effects.
    12

    Human vision versus camera capture

    Human vision integrates luminance over roughly 1/25–1/50 s and holds a signal briefly after the light stops (persistence), so a 3200 Hz pulse train fuses into a constant level. The eye also does not scan the scene in horizontal lines with a moving exposure window, so it produces no rolling bands.

    The same trace, seen two ways

    Top: the LED waveform. A wide eye window (left needle) settles on a steady value. A narrow camera window (right needle) reads a different value depending on where it sits — and a rolling-shutter sensor stacks those different readings down the frame as bands.

    • Short exposure window: a 1/1000 s shutter samples ~3 PWM periods — it cannot average what it did not capture.
    • Rolling shutter: each sensor line is exposed at a slightly different time; if the light modulates at the PWM, scan or OE frequency, successive lines catch different phases → bright and dark bands, which scroll if the frequencies drift.
    • PWM phase: each captured frame starts at a different point in the cycle → whole-frame flicker or slow beating over a sequence.
    • Colour separation: red, green and blue can have different duty cycles for a non-white colour, so a short exposure can catch more of one channel → a colour shift that is not in the content.
    Consequences for evidence A single photograph is not reliable evidence of how the display looks to a person — it is evidence of how the display looked to that camera, at that shutter, at that frame, at that phase. Two photos a fraction of a second apart can disagree. Video is more informative than a still. A display can be fully acceptable at 100% brightness and show artefacts at low brightness or on dark content, so acceptance testing must cover the brightness and content range that will actually be used.

    Common misconceptions

    What people say — and the correct statement
    MisconceptionCorrect statement
    “It’s a 3200 Hz display, so it’s camera-safe.”3200 Hz reduces artefact risk but does not guarantee a clean image at every brightness, content level, shutter and camera frame rate. Multiple other clocks (frame, scan, OE) are also present in the light.
    “50 Hz and 3200 Hz are the same measurement.”Different layers. 50 Hz = new pictures per second. 3200 Hz = pulse-pattern repetitions per second per LED. In our example, 64 repetitions per frame — a relationship, not an identity.
    “The scan file is a 50 Hz file, so the refresh is 50 Hz.”The scan file is configured for a 50 Hz system; its parameters produce a 3200 Hz PWM/grayscale refresh in the specified implementation.
    “Every 3840 Hz system is 60 Hz; every 3200 Hz system is 50 Hz.”A common design convention, not a rule. Some driver ICs generate PWM timing independently of the frame rate. Confirm from the scan file, datasheet, controller docs or measurement.
    “Lowering the brightness lowers the refresh rate.”Lowering brightness normally keeps the period (≈ 312.5 µs at 3200 Hz) and shortens the ON pulse. The refresh stays nominally the same; the modulation gets deeper.
    “Reducing current gain is always the best way to dim for camera.”It keeps pulses long but degrades colour accuracy, calibration validity, low-gray linearity and SNR. Most systems use a current-gain + PWM combination.
    “If the shutter covers a whole number of PWM periods, the image is clean.”Integer capture improves average-light integration but does not defeat rolling shutter, scan-frequency beats, OE timing, distributed PWM, refresh error or venue lighting.
    “1/800 s is always clean on a 3200 Hz display.”It captures 4 nominal periods and is a good starting point, but must still be verified for the specific installation.
    “The camera photo proves the display is faulty.”A photo proves what one camera captured in one phase. Reproduce it, vary the shutter, check the eye, and measure the optical waveform before concluding.
    “Scan ratio × grayscale % gives the real ON time.”That gives a rough upper bound only. Driver ICs schedule and split pulses in ways simple multiplication does not capture.
    “A faster camera shutter is always better for LED capture.”Shorter shutters capture fewer PWM periods and are more phase-sensitive. There is usually a best range, not “as fast as possible”.

Record the fundamental period(s), pulse width, modulation depth and any scan/OE structure — and whether the measured waveform changes with global brightness, grayscale level, colour and scan-file configuration. Do not rely only on the advertised “maximum refresh rate”.

      Acceptance conditions and customer responsibilities

      On-camera performance is a property of the complete system, not of the LED module alone. The complete system includes media frame rate and encoding, the playback computer, graphics-card timing, LED controller configuration, receiving-card firmware and parameters, the scan file, driver-IC operation, global brightness, displayed content, camera frame rate, camera shutter/exposure, camera sensor readout type, and venue lighting. A change to any of these can change the recorded result while the LED hardware is unchanged and fully within specification.

      What we commit to on a 50 Hz delivery

      When a system has been specified, configured, tested and accepted under the agreed 50 Hz configuration of section 04, we commit that — under that configuration and within the brightness and camera-shutter envelope recorded at acceptance — the display meets the agreed on-camera criteria.

      What requires joint re-validation

      Any change to the media frame rate or encoding, the playback configuration, the graphics-card output, the controller timing (or enabling frame-rate conversion), the receiving-card firmware or scan file, the global brightness operating point (in particular running darker than the recorded envelope), or the camera frame-rate / shutter range used on site.

      Shared responsibility — no automatic fault attribution An artefact appearing after a change does not by itself establish fault on either side. The supplier is responsible for delivering a display whose configured timing, scan file and driver operation meet the agreed specification, and for documenting the validated operating envelope clearly at acceptance. The customer / production is responsible for keeping the signal chain within the agreed configuration, and for bringing the real intended shooting conditions — expected camera models, frame rates, shutter ranges and the brightness operating point — into acceptance testing, not only to the site afterwards. Both parties should treat the brightness range and shutter range as first-class acceptance parameters, tested explicitly and recorded with photographic and oscilloscope evidence. The correct response to a dispute is to reproduce the condition, vary one parameter at a time, check against the human eye, and measure the optical waveform — then decide from evidence which layer changed.

      Field guide

      One page for technicians and camera operators. Print-friendly.

      Perimeter LED display — on-camera quick guide

      The four clocks

      • Content fps — want 25 or 50
      • GPU output Hz — want 50.00, not 59.94/60
      • PWM / grayscale refresh — 3200 Hz here (64 per frame)
      • Camera shutter — width of the recorded slice

      A 50 Hz signal and a 3200 Hz PWM refresh are different layers, not the same number.

      Our delivered 50 Hz chain

      Media 25/50 fps → player (no conversion) → GPU 50 Hz → controller in 50 / out 50, conversion off → validated scan file → driver PWM ≈ 3200 Hz → camera tested against this.

      Change any link → re-validate.

      Why the eye is fine but the camera isn’t

      The eye averages ~1/50 s and fills the gaps. A camera at 1/1000 s records a 1 ms slice (~3 PWM periods) and, on CMOS, reads line-by-line → bands, flicker, colour shifts. A photo shows what one camera caught in one phase.

      Camera starting points (3200 Hz / 50 Hz)

      • Frame rate: 50 or 25 fps (avoid 30/60/59.94)
      • Whole-period shutters: 1/50, 1/100, 1/200, 1/400, 1/800 s
      • Whole-period helps but does not guarantee clean
      • Use synchro-scan / anti-flicker to fine-tune; genlock if available

      Low brightness is the hard case

      Period stays 312.5 µs; the ON pulse shortens. 100%: looks continuous. 10%: ~31 µs spike in ~281 µs dark → artefacts far more likely. Test dark content and low brightness — not just white.

      Fast triage

      • Visible to the eye too? → display fault (data, power, calibration, scan file)
      • Changes with shutter? → PWM/scan/camera timing
      • Rolling bands? → rolling shutter vs PWM/scan — synchro-scan or genlock
      • Stationary bands? → scan/OE banding — check scan file with vendor
      • Worse when dimmed? → raise brightness or re-commission at the new point
      • Changes with camera angle/position? → beating with floodlights or another screen

      Golden rules. A high refresh number reduces risk; it does not guarantee a clean picture. Test at the real brightness and the real shutter speeds that will be used on air. Keep aperture, ISO, WB, zoom and content fixed while comparing shutters. When in doubt, measure the light with a photodiode + oscilloscope. If the chain changes, the previous result does not carry over.
